# 工业功能图标语义理解指南

本文件负责决定“这个功能到底应该画什么”。视觉风格、线面、重心、尺寸等规则由 `style-guide.md` 负责。

任何功能图标任务都必须先完成本文件的语义判断，再进入视觉设计。

## 1. 禁止看到功能名直接画

收到文案后，不得仅根据关键词直接联想图形。

例如 `DPF Regen`，不能只做“看到 DPF 就画 DPF，看到 Regen 就加循环箭头”。必须先理解完整功能含义，再决定最终视觉表达。

## 2. 每条文案拆成六个语义维度

对每一个功能逐条分析：

1. 功能本体：这句话本质上在做什么；
2. 核心对象：这个功能主要作用在什么对象上；
3. 核心动作：读取、清除、查询、更新、下载、打印、再生、检测等；
4. 状态或结果：功能最终呈现什么状态或变化；
5. 用户收益：用户真正获得什么，帮助判断卖点主次；
6. 同组区分点：它与最相近功能的关键区别是什么。

核心对象不等于产品设备。例如：

- Battery Test → 蓄电池
- ECU Information → ECU
- DPF Regen → DPF
- Diagnostic Reports → 诊断结果/报告
- Live Data → 实时车辆数据

## 3. 形成视觉语义句

完成六个维度后，将文案压缩成一句“用户需要从图标中看到什么”。

视觉语义句必须：

- 描述对象；
- 描述最重要的动作或状态；
- 不包含无关卖点；
- 不直接规定画法。

示例：

- Read Codes → “车辆诊断中的故障码正在被读取。”
- Clear Codes → “已经存在的车辆故障码被清除。”
- Live Data → “车辆参数正在持续实时变化。”
- ECU Information → “用户正在查看 ECU 模块的基础信息。”
- DPF Regen → “DPF 正在通过高温再生处理捕集的颗粒。”
- Diagnostic Reports → “诊断结果被整理为可查看或输出的报告。”

## 4. 判断用户已有认知来源

在设计新符号之前，先判断目标用户是否已经认识类似视觉符号。

### 车辆原生认知

来源：仪表盘警示灯、车内控制按钮、车辆系统状态符号、驾驶员常见提示。

适合 DPF、ABS、Engine、Brake、Fuel、Battery、Temperature、HVAC、Transmission、Derate 等车辆系统、警告或状态功能。

原则：借用司机已经熟悉的识别逻辑，不机械复制某个汽车品牌或车型的具体图形。

### 行业专业认知

来源：汽车维修、重卡维修、OBD 诊断、ECU/DTC、排放系统、电气系统、发动机系统等。

适合 ECU、DTC、OBD、DPF、Turbo、Transmission、Suspension、Fuel system 等。

可以借专业结构，但不能做成技术图纸、电路图、机械剖面或多部件系统示意图，只提取最具有识别度的代表性结构。

### 通用公共认知

例如：搜索→放大镜，删除→×/消除，下载→向下箭头，升级→向上/更新动作，打印→打印机/输出，文档→报告，Wi‑Fi→无线网络，保护→盾牌。

优先使用已有认知。品牌化应发生在结构、轮廓、线面、重心和负空间，而不是破坏符号认知。

### 产品操作认知

当功能直接描述产品本体或产品操作时，可以使用设备或产品局部，例如 Built-in Printer、Physical Buttons、Glare-Resistant Display、Standalone Device、Connector、Screen。

产品设备不是所有功能的默认主体。

### 结果/利益认知

有些抽象卖点无法通过明确实体直接表达，例如 Ease of Use、Compatibility、Safety Protection、Fast Scan、Free Update。此时可考虑用户最终得到的状态或结果，但仍优先寻找更直接的对象或动作。

## 5. 认知来源不是固定模板

一个功能可能同时对应多个认知来源。例如 DPF Regen 可同时参考车辆原生 DPF 认知、行业 DPF 结构和高温再生动作。

最终不是把所有来源都画进去，而是先利用这些来源理解用户认知，再提取最短视觉表达。

## 6. 每个功能比较 2–3 种表达方向

不能想到第一个方案就直接使用。

候选方案应从不同认知路径产生，然后比较：

1. 第一眼直观度；
2. 简洁度；
3. 用户已有认知；
4. 小尺寸适应性；
5. 与同组图标区分度；
6. 品牌视觉适配性。

优先选择综合表现最好的方案。

示例：DPF Regen 可比较：

- DPF 代表性过滤结构 + 简化热流；
- DPF 结构 + 捕集颗粒减少状态；
- DPF 结构 + 再生动作符号。

## 7. 表达选择优先级

默认顺序：

1. 直接对象；
2. 直接动作；
3. 明确状态/结果；
4. 产品设备；
5. 抽象隐喻。

越靠后越需要谨慎。

例如 Battery Test 优先使用蓄电池，不应优先使用“诊断设备 + 闪电”。

## 8. 设备使用判断

只有符合至少一个条件，设备才值得成为主体或重要组成：

- 卖点本身描述设备能力；
- 不出现设备会导致功能难以理解；
- 功能与设备物理结构直接相关；
- 用户明确要求产品语境。

Live Data、Battery Test、Diagnostic Reports、DPF Regen、Engine、ABS、Fuel、Turbo 等通常不需要设备，除非当前语境另有要求。

## 9. 图标不是文案的完整翻译

一句文案可能包含多个卖点，图标只负责最核心的视觉信息。

例如 `Lifetime Wi-Fi Updates — No Annual Update Fee` 不应同时绘制设备、Wi-Fi、云、更新箭头、`$0`、日历。先判断当前版面最主要卖点，剩余信息由文字承担。

原则：**图标和文案共同表达，不要求图标独立翻译全部信息。**

## 10. 短行业缩写强化认知

当主体具有高度通用的行业缩写，并且内部视觉过空时，可以考虑嵌入 ECU、ABS、DPF 等短缩写。

条件：

- 2–4 个字符为宜；
- 属于行业稳定认知；
- 嵌入主体内部；
- 不作为唯一识别依据；
- 小尺寸下即使文字不可读，主体仍应成立。

## 11. 复杂机械对象采用代表性结构

不要求真实还原整个机械系统。

- ECU：保留模块外轮廓与少量接口/引脚，不画大量电路纹理和线路；
- Engine：保留经典发动机块体轮廓与 1–2 个代表结构，不画活塞、复杂内部机械和大量管路；
- Battery：优先保留蓄电池整体外轮廓、顶部端子与必要正负极身份，不能完全抽象成闪电、电量条、波形；
- DPF：保留过滤/颗粒捕集代表结构与必要再生状态，不画完整排气系统和复杂剖面。

## 12. 系列语义规划

当功能数量达到 3 个及以上时，必须整体分析：

- 主体重复：是否多个功能都使用文档、放大镜、设备、箭头作为主体；
- 语义碰撞：重点检查 Read Codes vs DTC Lookup、Read Codes vs Clear Codes、Live Data vs Diagnostic Reports、ECU Information vs Read Codes 等；
- 主轮廓差异：即使不看内部细节，也应具有一定区分度。

不能让整组六个功能都变成“方框 + 不同小符号”。

## 13. 语义失败时必须回退

如果生成结果出现图形好看但意思不对、需要看标题才能猜、两个功能无法区分、过度使用设备导致真正对象消失，或表达了次要卖点而非核心卖点，则不得继续只调整线条或风格。

必须回到语义阶段重新判断：

1. 功能本体；
2. 核心对象；
3. 用户认知来源；
4. 视觉语义句；
5. 候选表达。

语义错误不能通过视觉美化解决。

## 14. 最终原则

始终优先：

- 熟悉 > 陌生
- 直接 > 绕弯
- 一个核心意思 > 完整翻译全文
- 用户认知 > 设计师炫技
- 识别效率 > 技术细节

在语义确认之前，不进入最终图标生成。
